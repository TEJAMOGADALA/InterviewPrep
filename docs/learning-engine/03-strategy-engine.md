# Executive Summary

The Strategy Engine is responsible for converting learner state into an actionable learning strategy.

While the Adaptive Learning Brain determines *what* should improve, the Strategy Engine determines *how* the learner should spend today's limited study time.

Its responsibility is not selecting individual topics.

Its responsibility is selecting the optimal preparation strategy.

Every mission generated by PrepOS is therefore the result of an explicit strategy rather than isolated ranking decisions.

---

# Purpose

The Strategy Engine exists to answer questions such as:

- What should dominate today's study session?
- Should coding or theory receive more attention?
- Should the learner continue the current module?
- Should weak topics override company priorities?
- Should revision increase today?
- Should preparation become broader or deeper?
- Is this the right time to switch modules?

---

# Scope

The Strategy Engine is responsible for:

- Selecting today's preparation strategy
- Allocating study budget
- Choosing primary/support/revision proportions
- Controlling cognitive load
- Maintaining mission stability
- Determining module progression
- Handling timeline-aware prioritization
- Resolving conflicting objectives

The Strategy Engine is NOT responsible for:

- Topic ranking
- Coding problem selection
- Revision scheduling
- Knowledge graph traversal
- Mastery calculation

# Design Philosophy

Every generated mission should satisfy five objectives.

1. Maximize interview success.
2. Respect company priorities.
3. Minimize cognitive overload.
4. Preserve learning continuity.
5. Improve long-term mastery.

The strategy should never optimize only one objective.

# Strategy Hierarchy

Every planning cycle begins by selecting exactly one primary strategy.

```
                Learner State
                      │
                      ▼
           Strategy Selection Layer
                      │
     ┌────────────────┼─────────────────┐
     ▼                ▼                 ▼
Learning       Recovery Strategy   Interview Mode
Strategy
```

Only one strategy can dominate a mission.

Supporting strategies may complement it.

# Available Strategies

## 1. Foundation Building

Purpose:

Establish strong conceptual understanding.

Characteristics:

- Theory heavy
- Easy coding
- High explanation
- Low difficulty
- Frequent prerequisite reinforcement

Typical users:

- Beginners
- Career switchers
- New modules

---

## 2. Balanced Learning

Purpose:

Maintain healthy progress across theory, coding and revision.

Composition:

Primary

60%

Support

20%

Coding

10%

Revision

10%

Used when:

- Stable progress
- Moderate timeline
- No major weaknesses

---

## 3. DSA Sprint

Purpose:

Maximize problem-solving ability.

Typical targets:

- Google
- Meta
- Uber
- Atlassian

Composition:

DSA Concepts

40%

Coding

35%

Core CS

15%

Revision

10%

Difficulty gradually increases.

---

## 4. Design Focus

Purpose:

Maximize LLD/HLD capability.

Typical companies:

- Oracle
- Microsoft
- Salesforce

Composition:

LLD

40%

HLD

25%

Java

20%

Revision

15%

---

## 5. Weakness Recovery

Purpose:

Repair critical weaknesses.

Triggers:

- Low confidence
- Poor coding accuracy
- Failed revisions
- Forgotten prerequisites

Priority:

Weakness overrides breadth.

---

## 6. Revision Intensive

Purpose:

Recover long-term retention.

Activated when:

Revision debt exceeds threshold.

Mission contains:

- Spaced repetition
- Mixed coding
- Memory reinforcement

---

## 7. Interview Crunch Mode

Activated when:

Preparation window is short.

Characteristics:

- High-impact topics only
- Company-specific preparation
- Minimal exploration
- Maximum interview ROI

---

## 8. Mastery Reinforcement

Purpose:

Transform completed topics into permanent knowledge.

Focus:

- Difficult questions
- Interview simulations
- Mixed revision
- Real-world applications

# Mission Stability

One of the fundamental principles of PrepOS.

The planner should not change direction every day.

Example:

Monday

Trees

Tuesday

Graphs

Wednesday

HashMap

Thursday

OS

Friday

Dynamic Programming

This destroys learning continuity.

Instead:

```
Week

↓

Module

↓

Topic

↓

Coding

↓

Revision
```

The learner should remain inside a module until strategic conditions justify a transition.

---

# Module-Based Planning

Planning occurs at module level before topic level.

Example

```
DSA

↓

Trees

↓

BST

↓

AVL

↓

Problems
```

Never randomly jump across unrelated modules.

Benefits:

- Better retention
- Lower cognitive switching
- Faster mastery

---

# Conflict Resolution

Multiple priorities often compete.

Example:

Weak DBMS

Google Interview

Short Timeline

Strong DSA

The Strategy Engine resolves conflicts using priority rules.

Priority Order

1. Timeline
2. Interview target
3. Critical weaknesses
4. Module continuity
5. Revision health
6. Personal preferences

---

# Cognitive Load Management

The planner should intentionally control mental fatigue.

Avoid:

- Multiple unrelated hard topics
- Heavy coding after exhausting theory
- Excessive context switching

Prefer:

- One primary module
- One supporting subject
- Focused coding
- Short revision

---

# Intentional Postponement

Not every weak topic should be fixed immediately.

Example:

Weak Networking

Target:

Google

Timeline:

20 Days

Decision:

Delay networking.

Increase DSA.

Reason:

Expected interview ROI is significantly higher.

Strategic postponement is an intelligent decision, not a failure.

---

# Difficulty Progression

Difficulty should evolve.

```
Concept

↓

Easy Problems

↓

Medium Problems

↓

Hard Problems

↓

Mixed Problems

↓

Interview Simulation
```

Never jump directly to Hard unless learner evidence supports it.

---

# Explainability

Every selected strategy should generate reasoning.

Example

Today's Strategy

DSA Sprint

Reason

- Google target
- DSA mastery below expected
- Timeline 90 days
- Trees module already active
- Coding performance improving

---

# Constraints

The Strategy Engine must never:

- Randomly switch modules
- Ignore company priorities
- Ignore learner timeline
- Overload a mission
- Repeat identical missions
- Select contradictory strategies simultaneously

---

# Failure Handling

If learner signals are insufficient:

Fallback strategy:

Balanced Learning

If company data is unavailable:

Use generic interview roadmap.

If timeline is unknown:

Assume medium-term preparation.

# Acceptance Criteria

The Strategy Engine is considered successful when:

- Strategy remains stable across similar learner states.
- Company priorities influence planning.
- Timeline changes alter strategy.
- Weaknesses are addressed appropriately.
- Missions maintain module continuity.
- Cognitive overload remains controlled.
- Every strategy is explainable.
